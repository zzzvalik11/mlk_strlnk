# Архитектура интеграции со сторонними сервисами Starlink Личный кабинет абонента

## 1. Обзор архитектуры

Приложение «Starlink Личный кабинет абонента» построено по паттерну Clean Architecture с разделением на три слоя: Domain (сущности, use cases), Data (репозитории, источники данных, API-клиенты), Presentation (экраны, виджеты, state-менеджмент). Бэкенд сервер выступает оркестратором между мобильным приложением и сторонними сервисами. Приложение никогда не обращается напрямую к внешним API — все запросы проходят через единый backend-proxy, что обеспечивает безопасность (SSL-сертификаты, учётные данные сторонних сервисов хранятся только на сервере), унификацию интерфейсов (приложение работает с одним JSON API независимо от количества внешних сервисов), кеширование и оптимизацию запросов, централизованное логирование и мониторинг.

Технологический стек: Flutter 3.x + Dart, State management: Riverpod, Routing: GoRouter, Модели: Freezed 4.x + json_serializable, Сетевой слой: Dio, CI/CD: GitHub Actions.

Архитектурный подход Clean Architecture предполагает строгое разделение ответственности между слоями. Domain слой содержит бизнес-сущности и правила, не зависящие от каких-либо фреймворков или внешних систем. Data слой реализует интерфейсы репозиториев, определённых в Domain, и отвечает за коммуникацию с внешними источниками данных, включая бэкенд-прокси, локальное кеширование и преобразование DTO в доменные модели. Presentation слой отвечает за отображение данных пользователю, управление состоянием экранов через Riverpod провайдеры и навигацию между экранами посредством GoRouter.

Бэкенд-прокси является критически важным компонентом системы, который выполняет функции посредника между мобильным приложением и всеми сторонними сервисами: биллинговой системой Starlink BSS, платёжным шлюзом Банка Русский Стандарт, системой быстрых платежей СБП, SMS-шлюзом Devino Telecom и сервисом push-уведомлений Firebase Cloud Messaging. Такой подход позволяет полностью изолировать клиентское приложение от деталей реализации внешних сервисов, исключить хранение учётных данных на мобильном устройстве и обеспечить единую точку контроля за всеми исходящими запросами.

Каждый запрос от мобильного приложения к бэкенду сопровождается JWT-токеном в заголовке Authorization, который был получен при авторизации через биллинговую систему BSS. Бэкенд валидирует токен, определяет идентификатор абонента и выполняет соответствующий запрос к нужному стороннему сервису, добавляя при необходимости собственные учётные данные (API-ключи, SSL-сертификаты). Результат преобразуется в унифицированный формат и возвращается приложению. В случае ошибки бэкенд нормализует её, скрывая технические детали внешних сервисов от клиента и предоставляя пользователю понятное сообщение.

Использование паттерна Repository в сочетании с Remote Data Sources позволяет абстрагировать источники данных от бизнес-логики. Каждый репозиторий может комбинировать данные из нескольких источников (например, PaymentRepository объединяет данные из BSS, РСБ и СБП), кешировать результаты для снижения нагрузки на сеть и трансформировать DTO-объекты в доменные модели. Это делает код поддерживаемым, тестируемым и готовым к расширению при подключении новых внешних сервисов.

## 2. Биллинговая система (Starlink BSS)

### 2.1 Назначение

Биллинговая система Starlink BSS (starlink-api v1.0.0) является основной системой учёта абонентов, управления услугами и тарифами, обработки платежей и формирования истории транзакций. Это базовый провайдер данных для большинства функций приложения: авторизация, профиль абонента, балансы, тарифы, история операций.

Биллинговая система BSS представляет собой центральный узел всей информационной инфраструктуры оператора связи Starlink. Она хранит полную информацию о каждом абоненте, включая персональные данные, контактную информацию, адрес обслуживания и привязанные лицевые счета. Каждый абонент может иметь один или несколько лицевых счетов, каждый из которых содержит набор подключённых услуг с привязанными тарифными планами. Система управляет жизненным циклом услуг: подключение, приостановка, возобновление, изменение тарифа, отключение.

BSS также отвечает за финансовый учёт: ведение балансов лицевых счетов, начисление абонентской платы, списание средств за оказанные услуги, формирование истории транзакций для каждого счёта. На основе данных BSS приложение отображает пользователю текущий баланс, список активных услуг с тарифами, доступные для подключения тарифные планы и дополнительные услуги, а также полную историю финансовых операций с возможностью фильтрации по датам.

Помимо операционных функций, BSS предоставляет интерфейсы для взаимодействия со сторонними системами: генерацию платёжных ссылок для пополнения счёта через платёжный шлюз РСБ, управление автоплатежами (подключение, отключение), обработку заявок на подключение новых услуг через магазин (shop), отправку email-уведомлений через службу поддержки. Система также поддерживает механизм обещанного платежа, позволяющий абоненту временно продлить оказание услуг при отрицательном балансе на определённых условиях.

### 2.2 Спецификация API

BSS предоставляет REST API по спецификации OpenAPI 3.1.0 со следующими группами эндпоинтов:

- **Авторизация**: POST /api/v1/auth/token (PIN + пароль → JWT, 365 дней), POST /api/v1/auth/logout.
- **Абонент**: GET /api/v1/subscriber (профиль), GET /api/v1/subscriber/accounts (список счетов).
- **Счета**: GET/PATCH /api/v1/subscriber/accounts/{account_id}, GET pay-link, auto-payment-off, auto-payment-link.
- **Услуги**: GET /services, PATCH /services/{service_id}, GET additional-services, tariffs.
- **Транзакции**: POST /api/v1/subscriber/accounts/{account_id}/transactions (с фильтрацией по датам).
- **Пакеты**: GET /api/v1/bundles, GET /api/v1/bundles/{bundle_id} (с тарифами).
- **Типы тарифов**: GET /api/v1/tariff-types.
- **Магазин**: POST /api/v1/subscriber/shop (заявки на подключение услуг).
- **Поддержка**: POST /api/v1/support/send-email.
- **Уведомления**: GET /api/v1/notifications/send, status, status-old (push через FCM).
- **Администрация**: GET /api/v1/webclient/groups, logs/user/{user_id}, logs/client/{client_id}.
- **Ресурсы**: GET /api/v1/resources/promised-pay-terms.

Авторизация в BSS осуществляется путём отправки POST-запроса на эндпоинт /api/v1/auth/token с параметрами username (PIN-код абонента, 6 цифр) и password (пароль, минимум 4 символа). При успешной аутентификации сервер возвращает JWT-токен со сроком действия 365 дней. Этот токен используется для авторизации всех последующих запросов к API BSS путём передачи его в заголовке Authorization: Bearer {jwt}. Выход из системы выполняется через POST /api/v1/auth/logout, который инвалидирует текущий токен на стороне сервера.

Эндпоинт профиля абонента GET /api/v1/subscriber возвращает полную информацию о текущем пользователе, включая список привязанных лицевых счетов. Каждый счёт содержит информацию о балансе, статусе (активен, заблокирован, приостановлен), наличии автоплатежа и подключённых услугах. Для получения детальной информации по конкретному счёту используется GET /api/v1/subscriber/accounts/{account_id}, а для обновления (например, приостановка услуги или активация обещанного платежа) — PATCH-запрос на тот же эндпоинт.

Управление услугами осуществляется через группу эндпоинтов /services, позволяющих просматривать список активных услуг, получать доступные тарифные планы для конкретной услуги, подключать и отключать дополнительные услуги, а также изменять тарифный план. Транзакции запрашиваются через POST /api/v1/subscriber/accounts/{account_id}/transactions с указанием дат начала и окончания периода, что позволяет пользователю просматривать историю финансовых операций с гибкой фильтрацией.

### 2.3 Схема интеграции

Бэкенд работает как прозрачный прокси для большинства запросов к BSS. Аутентификация в BSS происходит по JWT-токену, который получается при авторизации (POST /api/v1/auth/token). Мобильное приложение хранит токен локально (flutter_secure_storage) и передаёт в заголовке Authorization: Bearer {jwt} при каждом запросе к нашему бэкенду. Бэкенд, получив запрос, добавляет необходимые заголовки и пробрасывает его в BSS.

Схема интеграции с биллинговой системой построена по принципу прозрачного проксирования: бэкенд получает запрос от мобильного приложения, извлекает JWT-токен пользователя из заголовка Authorization, валидирует его и转发 запрос к соответствующему эндпоинту BSS. При этом бэкенд может добавлять дополнительные заголовки, выполнять логирование запроса и ответа, а также трансформировать формат данных если это необходимо для унификации.

Особое внимание уделяется обработке авторизации: при первом запросе на вход (POST /auth/login) бэкенд переадресует учётные данные (PIN и пароль) в BSS, получает JWT-токен и возвращает его приложению. Все последующие запросы приложения содержат этот токен, и бэкенд просто пробрасывает его в BSS без дополнительной обработки. При истечении срока действия токена или его инвалидации бэкенд возвращает приложению ошибку 401, что инициирует повторную авторизацию пользователя.

Для оптимизации производительности бэкенд может кешировать редко изменяющиеся данные из BSS, такие как список доступных тарифных планов, типов тарифов, пакетов услуг и условий обещанного платежа. Кеш обновляется по расписанию или при явной инвалидации. Данные, зависящие от конкретного абонента (баланс, транзакции, активные услуги), кешируются на короткий срок или не кешируются вовсе для обеспечения актуальности информации.

### 2.4 Модели данных (Domain слой)

- **CustomerResponse**: id, full_name, phone, email, address.
- **AccountResponse**: id, account_number, balance, status (active/blocked/suspended), has_auto_payment, auto_payment_amount.
- **ServiceItem**: id, name, status, tariff {id, name, price}.
- **Transaction**: date, amount, description, type (credit/debit).
- **Bundle**: id, name, description, is_active, tariffs.
- **TariffType**: id, name, description, is_enabled.

Модели доменного слоя определены с использованием библиотеки Freezed, что обеспечивает иммутабельность, генерацию методов copyWith и объединение (union types) для перечислений. Каждая модель сопровождается генератором сериализации json_serializable для преобразования между JSON-ответами API и объектами Dart. DTO-модели (Data Transfer Objects) из слоя Data преобразуются в доменные модели внутри репозиториев, что полностью изолирует бизнес-логику от формата данных внешних сервисов.

CustomerResponse содержит полную информацию об абоненте, включая уникальный идентификатор, ФИО, контактный телефон, электронную почту и адрес обслуживания. AccountResponse описывает лицевой счёт с номером, текущим балансом, статусом (активен, заблокирован, приостановлен) и флагами наличия автоплатежа с указанием суммы. ServiceItem представляет подключённую услугу с её наименованием, статусом и привязанным тарифным планом, включающим идентификатор, название и стоимость. Transaction отражает отдельную финансовую операцию с датой, суммой, описанием и типом (поступление или списание). Bundle описывает пакет услуг с информацией о доступных тарифных планах, а TariffType определяет категорию тарифа с флагом доступности для подключения.

## 3. Платёжный шлюз — Банк Русский Стандарт (RSB ECOMM)

### 3.1 Назначение

Платёжная платформа RSB ECOMM v3.0.17 предназначена для обработки карточных платежей через интернет-эквайринг Банка Русский Стандарт. Обеспечивает приём оплаты банковскими картами (Visa, Mastercard, Мир), поддержку 3D Secure 2.x, работу по моделям SMS (единая транзакция) и DMS (двухэтапная: авторизация + выполнение), рекуррентные платежи по сохранённым картам, оплату через Apple Pay, Google Pay, Samsung Pay, Yandex Pay, оплату через Систему быстрых платежей (СБП).

Платёжная платформа RSB ECOMM является ядром финансовой инфраструктуры приложения, обеспечивая полный цикл обработки карточных платежей. Поддержка протокола 3D Secure 2.x гарантирует безопасность транзакций, требуя дополнительной аутентификации держателя карты через банк-эмитент. Это существенно снижает риск мошеннических операций и соответствует требованиям платёжных систем Visa и Mastercard.

Модель SMS (Single Message System) представляет собой одностадийную транзакцию, при которой авторизация и выполнение происходят в рамках одного запроса — средства блокируются и сразу списываются. Это основной метод оплаты в приложении, подходящий для большинства сценариев пополнения лицевого счёта абонента. Модель DMS (Dual Message System) предусматривает двухэтапную обработку: на первом этапе средства блокируются на карте клиента (авторизация), а на втором — фактически списываются (выполнение). Это позволяет резервировать сумму до подтверждения оказания услуги.

Рекуррентные платежи позволяют автоматически списывать средства с сохранённой карты абонента по расписанию для регулярной оплаты услуг связи. Для этого используется механизм сохранения реквизитов карты (команда -z) с последующим регулярным списанием (команда -e). Платформа также поддерживает кошельки и платёжные системы Apple Pay, Google Pay, Samsung Pay и Yandex Pay, что расширяет доступные методы оплаты для пользователей различных мобильных платформ. Интеграция с Системой быстрых платежей позволяет принимать оплату через QR-коды без ввода реквизитов карты.

### 3.2 Спецификация

RSB ECOMM поддерживает два метода интеграции: **HTTP POST** к Merchant Handler URL (основной) и **REST API** с JWT Bearer аутентификацией (JSON API формат). Наш бэкенд использует HTTP POST метод.

**Схема работы (платёжная форма на стороне Банка):**

1. ТСП регистрирует транзакцию (POST к Merchant Handler URL).
2. Банк возвращает transaction_id.
3. ТСП перенаправляет клиента на ClientHandler URL с trans_id.
4. Клиент вводит карту и проходит 3DS.
5. Банк перенаправляет на RETURN_URL.
6. ТСП запрашивает статус (команда -c).

**URL-адреса:**

- Production Merchant Handler: https://3dsecurepay.rsb.ru/ecomm2/MerchantHandler
- Production ClientHandler: https://3dsecurepay.rsb.ru/ecomm2/ClientHandler?trans_id={trans_id}
- Test Merchant Handler: https://testsecurepay2.rsb.ru:9443/ecomm2/MerchantHandler
- Test ClientHandler: https://testsecurepay2.rsb.ru:9443/ecomm2/ClientHandler?trans_id={trans_id}

**Аутентификация:** SSL-сертификат ТСП (TLS 1.2+). Сертификат выдаётся Банком, срок действия — 1 год. Организация обязана контролировать актуальность.

Выбор HTTP POST метода интеграции обусловлен его простотой и надёжностью. Все команды передаются как form-urlencoded параметры в теле POST-запроса. Аутентификация осуществляется посредством взаимного SSL (mTLS): бэкенд предоставляет клиентский SSL-сертификат, выданный Банком Русский Стандарт, при установлении соединения. Это обеспечивает двустороннюю проверку подлинности как сервера Банка, так и нашего бэкенда.

Схема с платёжной формой на стороне Банка (Redirect Model) выбрана для минимизации требований к сертификации PCI DSS. Поскольку карточные данные вводятся на серверах Банка Русский Стандарт, наше приложение и бэкенд не получают и не обрабатывают номер карты, CVV/CVC и другие чувствительные реквизиты. Клиент перенаправляется на платёжную страницу Банка по HTTPS, где проходит полный цикл ввода данных карты и аутентификации 3D Secure, после чего возвращается на наш бэкенд через RETURN_URL.

Среда разработки и тестирования использует отдельный набор URL-адресов на домене testsecurepay2.rsb.ru с портом 9443. Это позволяет проводить полное тестирование платёжного цикла с тестовыми картами без риска воздействия на боевые транзакции. При развёртывании в продуктивную среду бэкенд переключается на production URL (3dsecurepay.rsb.ru) посредством переменных окружения.

### 3.3 Команды платёжного шлюза

Все команды передаются как HTTP POST с параметрами формы. Ключевой параметр `command` определяет операцию:

| Команда | Параметр | Описание | Обязательные параметры |
|---------|----------|----------|----------------------|
| Регистрация SMS | -v | Единая транзакция (авторизация + выполнение) | amount, currency, client_ip_addr |
| Запрос статуса | -c | Результат транзакции | trans_id, client_ip_addr |
| DMS авторизация | -a | Блокировка средств (без списания) | amount, currency, client_ip_addr |
| DMS выполнение | -t | Списание заблокированных средств | trans_id, amount, currency, client_ip_addr |
| Отмена | -r | Отмена до закрытия бизнес-дня | trans_id |
| Возврат | -k | Возврат после закрытия бизнес-дня | trans_id, amount (опционально) |
| Закрытие дня | -b | Инициация расчётов (1 раз/сутки) | — |
| Рекуррент (сохранение) | -z | Сохранение карты + SMS платёж | amount, currency, biller_client_id, perspayee_expiry, perspayee_gen=1 |
| Рекуррент (оплата) | -e | Оплата по сохранённой карте | amount, currency, biller_client_id |

**Формат сумм:** целые единицы, последние 2 цифры — копейки (12300 = 123.00 руб.).

**Код валюты:** 643 (российский рубль, ISO 4217).

Команда регистрации SMS-транзакции (-v) является наиболее часто используемой в приложении. При её вызове бэкенд передаёт сумму платежа в копейках (например, 500 рублей = 50000), код валюты 643, IP-адрес клиента и опциональное описание операции. В ответ Банк возвращает уникальный transaction_id, который используется для формирования ссылки на платёжную страницу (ClientHandler) и последующего запроса статуса транзакции.

Команда запроса статуса (-c) вызывается после возврата клиента с платёжной страницы Банка для определения итогового результата транзакции. Бэкенд может вызывать её многократно с интервалом, реализуя механизм polling, пока не будет получен финальный статус (OK/ERROR/REJECTED). Команды DMS (-a и -t) зарезервированы для сценариев, требующих предварительной блокировки средств, например, при оформлении заказа с отложенным подтверждением.

Команды отмены (-r) и возврата (-k) используются для обратных операций. Отмена применяется до закрытия бизнес-дня Банка и возвращает полную сумму без дополнительной комиссии. Возврат выполняется после закрытия бизнес-дня и поддерживает как полный, так и частичный возврат средств. Команда закрытия дня (-b) должна вызываться один раз в сутки (обычно поздно вечером) для инициации расчётов с Банком. Рекуррентные команды (-z и -e) обеспечивают автоматическое списание по сохранённой карте для реализации функции автоплатежа.

### 3.4 Статусы транзакций

- **RESULT**: OK / ERROR / REJECTED
- **RESULT_PS**: FINISHED (SMS завершена), ACTIVE (DMS авторизована, ожидает выполнения), REVERSED (отменена)
- **RESULT_CODE**: 000 — успех, другие коды — ошибки (1001 — системная, 400 — отменена, 500 — бизнес-день закрыт и т.д.)
- **3DSECURE**: AUTHENTICATED / NOT_AUTHENTICATED / FAILED

Понимание статусов транзакций критически важно для корректной работы платёжного функционала приложения. Поле RESULT содержит итоговый результат операции: OK означает успешное завершение, ERROR указывает на техническую или бизнесовую ошибку, REJECTED означает отказ со стороны банка-эмитента или платёжной системы. Поле RESULT_PS уточняет состояние транзакции в платёжной системе: FINISHED означает полное завершение одностадийной транзакции, ACTIVE указывает на успешную авторизацию в рамках DMS-модели с ожиданием выполнения, REVERSED означает отмену ранее выполненной операции.

Поле RESULT_CODE содержит числовой код, детализирующий результат. Код 000 означает безусловный успех. Код 100 указывает на общий отказ (decline) от банка-эмитента, 116 — на недостаточность средств на карте, 121 — на превышение лимита операций. Код 400 сигнализирует об отмене операции, 500 — о невозможности выполнения из-за закрытого бизнес-дня, 701 — о неверном или отсутствующем transaction_id, 1001 — о системной ошибке на стороне платёжного шлюза. Бэкенд маппит эти коды на понятные для пользователя сообщения и стандартизированные статусы API.

Поле 3DSECURE отражает результат прохождения аутентификации 3D Secure: AUTHENTICATED — держатель карты успешно прошёл проверку, NOT_AUTHENTICATED — проверка не пройдена (но транзакция может быть всё равно одобрена), FAILED — ошибка в процессе 3D Secure аутентификации. Бэкенд учитывает эти статусы при определении финального результата оплаты и формировании соответствующего уведомления для пользователя.

### 3.5 Схема интеграции в приложении

Мобильное приложение не хранит реквизиты карт. Поток оплаты картой:

1. Приложение запрашивает ссылку на оплату (GET /v1/subscriber/accounts/{id}/pay-link?amount=...&payment_method=card).
2. Бэкенд формирует запрос к РСБ (команда -v), получает transaction_id.
3. Бэкенд возвращает URL платежной формы (ClientHandler).
4. Приложение открывает WebView/InAppBrowser с этим URL.
5. Клиент вводит карту, проходит 3DS.
6. РСБ перенаправляет на RETURN_URL (наш бэкенд).
7. Бэкенд перенаправляет в приложение (deep link).
8. Приложение запрашивает статус (POST /v1/payments/card/status).
9. Бэкенд опрашивает РСБ (команда -c) и возвращает результат.

Схема интеграции построена с соблюдением принципа минимального доверия: мобильное приложение никогда не получает доступ к карточным данным, SSL-сертификатам или учётным данным платёжного шлюза. Весь цикл оплаты инициируется приложением, но выполняется между бэкендом и Банком Русский Стандарт.

На первом этапе приложение отправляет запрос на получение платёжной ссылки, указывая сумму пополнения и идентификатор лицевого счёта. Бэкенд формирует запрос к Merchant Handler РСБ с командой -v (регистрация SMS-транзакции), передавая сумму в копейках, код валюты 643 и IP-адрес клиента. В ответ РСБ возвращает transaction_id, который бэкенд использует для формирования URL платёжной формы ClientHandler. Этот URL возвращается приложению в ответе API.

Приложение открывает полученный URL во встроенном WebView (InAppBrowser), где клиент видит платёжную страницу Банка, вводит реквизиты карты и проходит процедуру 3D Secure. После завершения оплаты Банк перенаправляет клиента на RETURN_URL, который указывает на endpoint нашего бэкенда. Бэкенд обрабатывает этот redirect, извлекает transaction_id из параметров запроса, немедленно запрашивает статус транзакции у РСБ (команда -c) и перенаправляет клиента обратно в мобильное приложение через зарегистрированный deep link.

Приложение, получив deep link, инициирует финальный запрос статуса платежа к бэкенду. Бэкенд выполняет повторный запрос статуса к РСБ для подтверждения результата и возвращает приложению стандартизированный ответ с финальным статусом (success, failed, pending, expired). При успешной оплате бэкенд также инициирует обновление баланса в биллинговой системе и отправку push-уведомления через FCM.

### 3.6 Коды ответов RESULT_CODE (основные)

000 — Успешно, 100 — Decline (общий отказ), 116 — Недостаточно средств, 121 — Превышен лимит, 400 — Операция отменена, 500 — Бизнес-день закрыт, 701 — Неверный транзакционный ID, 1001 — Системная ошибка.

Код 000 является единственным кодом успешного выполнения операции. Все остальные коды сигнализируют о различных типах ошибок, которые бэкенд обрабатывает и преобразует в пользовательские сообщения. Код 100 (Decline) означает общий отказ банка-эмитента без уточнения причины — это наиболее частый код при проблемах с картой. Код 116 явно указывает на недостаточность средств, что позволяет приложению отобразить соответствующее сообщение. Код 121 означает превышение лимита операций по карте, установленного банком-эмитентом.

Код 400 указывает на то, что операция была отменена (например, клиент закрыл платёжную страницу или нажал кнопку отмены). Код 500 означает, что бизнес-день Банка уже закрыт и новые операции невозможны до следующего дня — это требует особой обработки, поскольку закрытие бизнес-дня выполняется нашей системой один раз в сутки. Код 701 указывает на отсутствие или недействительность transaction_id, что может произойти при повторном запросе статуса уже обработанной транзакции. Код 1001 является критической системной ошибкой на стороне платёжного шлюза, требующей оповещения технической поддержки.

## 4. Система быстрых платежей (СБП)

### 4.1 Назначение

Система быстрых платежей (СБП) — платёжная система оперируемая НСПК, позволяющая мгновенно переводить деньги по QR-коду или телефонному номеру между счетами разных банков. В контексте приложения Starlink СБП используется как метод пополнения лицевого счёта абонента.

Система быстрых платежей является современным платежным инструментом, развитие которого инициировано Центральным Банком Российской Федерации и оперируется Национальной системой платёжных карт (НСПК). СБП обеспечивает мгновенные переводы денежных средств между счетами в разных банках-участниках системы, что делает его идеальным решением для пополнения лицевого счёта абонента оператора связи.

В контексте приложения Starlink СБП предлагается пользователю как альтернативный метод оплаты наряду с оплатой банковской картой через платёжный шлюз РСБ. Основное преимущество СБП для пользователя — не требуется вводить реквизиты карты, достаточно открыть банковское приложение и подтвердить платёж. Это снижает барьер входа и повышает конверсию платежей, особенно для пользователей, предпочитающих мобильные банковские приложения.

Интеграция СБП в приложение реализована через агрегатора — Сбербанк, который предоставляет промежуточное REST API для создания платежей, получения статусов, отмены и возврата. Наш бэкенд взаимодействует исключительно с API агрегатора, а агрегатор обеспечивает взаимодействие с НСПК и банками-участниками. Такой подход упрощает интеграцию, поскольку все复杂性 взаимодействия с банками-участниками берёт на себя агрегатор.

### 4.2 Спецификация API

СБП (через Сбербанк) — OpenAPI 3.1.0, 5 рабочих эндпоинта:

- **POST /api/v1/create** — создание платежа. Запрос: amount (number, рубли), account (string, до 6 символов — номер лицевого счёта), phone (string, опционально), email (string, опционально), payment_stat (string, default: sbpStat). Ответ: success, sbp_id, rq_uid, order_id, qrcode_link (ссылка для QR), qr_url (URL формы оплаты), amount, status.
- **GET /api/v1/status/{order_id}** — статус платежа. Ответ: success, sbp_id, rq_uid, order_id, status, amount, account, created_at, operation_time.
- **GET /api/v1/cancel/{order_id}** — отмена. Ответ: success, sbp_id, order_id, status, message.
- **POST /api/v1/refund/{order_id}** — возврат (полный/частичный). Запрос: amount (опционально). Ответ: success, sbp_id, order_id, status, refund_amount, message.
- **POST /api/v1/callback** — входящий callback от Сбербанка/НСПК. Данные: mdOrder, orderNumber, operation, status (0/1), additionalParams.

API СБП через агрегатора Сбербанка предоставляет пять основных эндпоинтов, покрывающих полный жизненный цикл платежа. Эндпоинт создания платежа принимает сумму в рублях (в отличие от РСБ, где сумма передаётся в копейках), номер лицевого счёта абонента и опциональные контактные данные. В ответ возвращается уникальный order_id, ссылка для генерации QR-кода (qrcode_link) и URL формы оплаты (qr_url).

Эндпоинт статуса позволяет запросить текущее состояние платежа по order_id. Этот эндпоинт используется приложением для polling-проверки статуса после отображения QR-кода. Эндпоинт отмены позволяет инициировать отмену созданного, но ещё не оплаченного платежа. Эндпоинт возврата поддерживает как полный, так и частичный возврат средств после успешной оплаты. Эндпоинт callback принимает входящие уведомления от Сбербанка/НСПК об изменении статуса платежа, что позволяет бэкенду оперативно реагировать на события без необходимости постоянного опроса.

Важно отметить, что СБП использует статусную модель с множеством возможных состояний, отличных от модели РСБ. Каждый статус имеет чёткую семантику и определяет доступные действия с платежом. Бэкенд выполняет маппинг статусов СБП на унифицированную модель статусов приложения, обеспечивая консистентное отображение информации пользователю независимо от выбранного метода оплаты.

### 4.3 Статусы платежа СБП

PaymentState enum: CREATED (создан), ON_PAYMENT (в процессе оплаты), PAID (оплачен), DECLINED (отклонён), EXPIRED (истёк срок), REVERSED (отменён), REFUNDED (возврат выполнен), REVOKED (аннулирован), AUTHORIZED (авторизован), CONFIRMED (подтверждён).

Статусная модель СБП включает десять возможных состояний, каждое из которых отражает определённый этап жизненного цикла платежа. CREATED означает, что платёж успешно создан в системе и ожидает оплаты клиентом — на этом этапе приложение должно отобразить QR-код или платёжную ссылку. ON_PAYMENT указывает на то, что клиент инициировал процесс оплаты через банковское приложение, но операция ещё не завершена.

AUTHORIZED и CONFIRMED — промежуточные статусы, отражающие процесс авторизации и подтверждения платежа в банковской системе. PAID является финальным успешным статусом, означающим, что средства зачислены на счёт получателя. DECLINED указывает на отказ банка-отправителя в проведении операции. EXPIRED означает, что срок действия платёжной ссылки или QR-кода истёк и оплата больше невозможна.

REVERSED и REVOKED означают отмену платежа на разных этапах: REVERSED — отмена уже проведённого платежа, REVOKED — аннулирование до завершения. REFUNDED указывает на успешное выполнение операции возврата средств. Бэкенд маппит эти статусы на унифицированную модель: CREATED/ON_PAYMENT → pending, PAID → success, DECLINED → failed, REVERSED/REVOKED → refunded, EXPIRED → expired.

### 4.4 Схема интеграции

Поток оплаты через СБП:

1. Приложение запрашивает ссылку на оплату (GET /v1/subscriber/accounts/{id}/pay-link?amount=...&payment_method=sbp).
2. Бэкенд создаёт платёж в СБП (POST /api/v1/create) с номером лицевого счёта.
3. Бэкенд возвращает qrcode_link и qr_url.
4. Приложение отображает QR-код (или открывает qr_url в браузере).
5. Клиент сканирует QR банковским приложением и подтверждает платёж.
6. Сбербанк присылает callback на наш бэкенд (POST /v1/payments/sbp/callback).
7. Бэкенд обновляет статус платежа в своей БД.
8. Приложение может также опрашивать статус (GET /v1/payments/sbp/status/{order_id}).

Интеграция СБП в приложение реализована по двухканальной модели: основной канал — входящий callback от Сбербанка при изменении статуса, резервный канал — polling-запросы от приложения. Callback-модель обеспечивает мгновенное обновление статуса: как только клиент подтверждает платёж в банковском приложении, Сбербанк отправляет уведомление на наш бэкенд, который обновляет статус платежа в базе данных и отправляет push-уведомление приложению через FCM.

Резервный polling-канал необходим для ситуаций, когда callback по каким-либо причинам не доставлен (сетевые проблемы, задержки). Приложение периодически (например, каждые 3-5 секунд) запрашивает статус платежа у бэкенда, который при необходимости уточняет его у агрегатора СБП. Polling прекращается по достижении финального статуса (PAID, DECLINED, EXPIRED) или по истечении таймаута (обычно 10-15 минут).

Отображение QR-кода в приложении реализуется двумя способами: непосредственная генерация QR-кода из qrcode_link с помощью библиотеки qr_flutter (для отображения внутри приложения) или открытие qr_url во внешнем браузере/банковском приложении (для перехода по платёжной ссылке). Первый вариант предпочтителен для iOS и Android, поскольку позволяет пользователю оставаться в приложении и сканировать QR другим устройством или сделать скриншот.

### 4.5 СБП через РСБ ECOMM

РСБ также поддерживает СБП на своей платёжной странице. Для этого в запрос регистрации (команды -v или -a) добавляется параметр `ecomm_payment_scenario=10564`. Клиент увидит кнопку СБП на платёжной форме Банка. Возвраты через СБП в РСБ выполняются стандартной командой -k, для чего необходима ЭЦП (приватный ключ и сертификат, созданные через OpenSSL).

Дублирование поддержки СБП через платёжный шлюз РСБ обеспечивает резервный канал приёма быстрых платежей. При использовании этого сценария клиент направляется на платёжную страницу Банка Русский Стандарт, где наряду с полями ввода реквизитов карты отображается кнопка «Оплатить через СБП». При нажатии на эту кнопку открывается стандартный интерфейс СБП с выбором банка и подтверждением платежа.

Параметр ecomm_payment_scenario=10564 указывает платёжному шлюзу РСБ на необходимость активации СБП-канала на платёжной странице. Это позволяет использовать единый поток интеграции (через Merchant Handler и ClientHandler) для всех методов оплаты, включая карты и СБП. Для возвратов через СБП в рамках РСБ используется стандартная команда -k, однако она требует усиленной аутентификации с помощью ЭЦП — цифрового подписания запроса приватным ключом организации. Ключ и сертификат ЭЦП генерируются через утилиту OpenSSL и хранятся в secure vault на бэкенде.

## 5. SMS-шлюз — Devino Telecom

### 5.1 Назначение

Devino Telecom — провайдер SMS-сообщений для бизнеса. В приложении Starlink используется для: отправки одноразовых паролей (OTP) при авторизации, уведомлений о платежах (подтверждение списания), информационных сообщений (задолженность, блокировка), уведомлений техподдержки.

Devino Telecom является сертифицированным оператором массовых SMS-рассылок, обеспечивающим доставку сообщений на номера всех российских мобильных операторов. В контексте приложения Starlink SMS-шлюз выполняет критически важную функцию доставки одноразовых паролей (OTP) для двухфакторной аутентификации абонентов. При вводе PIN-кода и пароля бэкенд инициирует отправку OTP на зарегистрированный номер телефона абонента, который необходимо ввести в приложении для завершения авторизации.

Помимо OTP, Devino используется для отправки транзакционных уведомлений: подтверждения списания средств при оплате через РСБ или СБП, информирования о зачислении средств на лицевой счёт, предупреждений о низком балансе и приближающейся блокировке услуг. Эти уведомления обеспечивают прозрачность финансовых операций для абонента и повышают доверие к сервису.

SMS также используется как канал информирования о статусе обращений в техническую поддержку: подтверждение регистрации тикета, уведомление о принятии в работу, информирование о ответе оператора. В случае, если push-уведомление через FCM не было доставлено (например, при отсутствии интернет-соединения), SMS служит резервным каналом оповещения абонента о важных событиях.

### 5.2 Спецификация API

Devino REST API v2, базовый URL: https://integrationapi.net

Аутентификация: Basic Auth (login:password).

Эндпоинты:

- **POST /v2/Send/SMS** — отправка SMS. Параметры: DestinationAddress (номер, формат 7XXXXXXXXXX), Text (текст), SourceAddress (имя отправителя), SendDate (опционально, отложенная отправка). Ответ: Id (формат MT-XXXXXXXXX), State.
- **GET /v2/MessageState/{id}** — статус доставки. Ответ: State (Delivered, Sent, Expired, Undeliverable, Rejected), StateDescription.
- **GET /v2/User/Balance** — баланс аккаунта. Ответ: Balance, Currency (RUR).

API Devino v2 представляет собой простой REST-интерфейс с тремя основными эндпоинтами. Аутентификация выполняется по протоколу HTTP Basic Auth — логин и пароль Devino кодируются в Base64 и передаются в заголовке Authorization. Все запросы выполняются по HTTPS, обеспечивая защиту учётных данных в транзите.

Эндпоинт отправки SMS принимает номер получателя в формате 7XXXXXXXXXX (11 цифр, без знака +), текст сообщения (ограничение по длине — 70 символов для латиницы, 70 символов для кириллицы в кодировке UCS-2), имя отправителя (зарегистрированное в Devino альфа-имя, например «Starlink») и опционально дату отложенной отправки. В ответ возвращается уникальный идентификатор сообщения в формате MT-XXXXXXXXX, который используется для последующего запроса статуса доставки.

Эндпоинт статуса доставки позволяет проверить текущее состояние отправленного SMS: Delivered (доставлено на устройство), Sent (передано оператору связи), Expired (истёк срок доставки), Undeliverable (невозможно доставить — номер заблокирован или не существует), Rejected (отклонено оператором). Эндпоинт баланса аккаунта возвращает текущий остаток средств на счёте Devino в рублях, что используется для мониторинга и своевременного пополнения баланса.

### 5.3 Схема интеграции

Мобильное приложение не отправляет SMS напрямую. Поток:

1. Бэкенд определяет необходимость отправки SMS (запрос OTP, уведомление).
2. Бэкенд формирует запрос к Devino API с Basic Auth.
3. Devino отправляет SMS на номер абонента.
4. Бэкенд сохраняет sms_id для последующей проверки статуса.
5. Callback от Devino (если настроен) или периодический опрос статуса.

Прокси-эндпоинты в нашем API: POST /v1/sms/send, GET /v1/sms/status/{sms_id}, GET /v1/sms/balance.

Полная изоляция SMS-отправки от мобильного приложения является ключевым требованием безопасности. Приложение инициирует отправку только опосредованно: при запросе OTP через endpoint авторизации, при срабатывании триггера уведомления о платеже, или при создании обращения в поддержку. Все решения об отправке SMS принимает бэкенд на основе бизнес-логики.

При отправке OTP бэкенд генерирует случайный числовой код (обычно 6 цифр), сохраняет его в кеше с привязкой к идентификатору сессии пользователя и ограничением по времени жизни (180 секунд), затем формирует запрос к Devino API. Текст SMS-сообщения генерируется из шаблона, например «Ваш код подтверждения: 482916. Действует 3 мин.». Rate limiting обеспечивает не более одного OTP-запроса на номер в 60 секунд и не более 3 попыток ввода кода.

Для уведомлений о платежах бэкенд получает webhook/callback от платёжного шлюза РСБ или от СБП, формирует текст уведомления с суммой и новым балансом, и отправляет SMS через Devino. Статус доставки отслеживается асинхронно: при получении финального статуса (Delivered, Expired, Undeliverable) бэкенд обновляет соответствующую запись в базе данных. Мониторинг баланса аккаунта Devino выполняется по расписанию (ежедневно) с автоматическим оповещением технической поддержки при падении ниже порогового значения.

## 6. Push-уведомления — Firebase Cloud Messaging (FCM)

### 6.1 Назначение

Push-уведомления используются для: информирования о завершении платежа, напоминаний об оплате, уведомлений о смене тарифа/услуги, информационных сообщений от оператора.

Firebase Cloud Messaging является основным каналом оперативного оповещения пользователей приложения о событиях, требующих их внимания. В отличие от SMS, push-уведомления бесплатны для отправителя, доставляются мгновенно, поддерживают богатый формат (заголовок, тело, данные, звук, бейдж) и обеспечивают двустороннее взаимодействие через data-payload.

Уведомления о завершении платежа информируют абонента об успешном или неуспешном пополнении лицевого счёта, что особенно важно при оплате через СБП, где клиент может не находиться в приложении в момент зачисления средств. Напоминания об оплате предупреждают о низком балансе или приближающемся списании абонентской платы, мотивируя абонента своевременно пополнить счёт и избежать блокировки услуг.

Уведомления о смене тарифа или подключении/отключении услуги информируют абонента об изменениях в его аккаунте, которые могли быть инициированы через другие каналы (колл-центр, офис обслуживания). Информационные сообщения от оператора позволяют доводить до абонентов важные новости, акции и уведомления о плановых технических работах. Все push-уведомления категоризируются, и пользователь может управлять подпиской на каждую категорию через настройки уведомлений в приложении.

### 6.2 Спецификация

FCM HTTP v1 API (googleapis.com/fcm/v1/projects/{project}/messages:send).

Аутентификация: OAuth 2.0 Service Account (серверный ключ). Формат: JSON Web Token.

Эндпоинты биллинга (прокси): GET /v1/notifications/send (инициировать рассылку), GET /v1/notifications/status, GET /v1/notifications/status-old.

FCM HTTP v1 API является современной версией протокола отправки push-уведомлений от Google, пришедшей на смену устаревшему Legacy API. Бэкенд аутентифицируется в Google Cloud с использованием сервисного аккаунта (Service Account), credentials которого хранятся в виде JSON-файла в переменной окружения. Аутентификация выполняется по протоколу OAuth 2.0 с получением JWT-токена, действительного 1 час, с автоматическим обновлением.

Каждое push-уведомление состоит из двух частей: notification (визуальная часть, отображаемая в системном трее) и data (пользовательские данные, обрабатываемые приложением). В notification указываются title и body текста, звук и иконка. В data передаются тип уведомления, идентификатор связанной сущности (например, payment_id) и целевой экран для навигации при нажатии на уведомление.

Для Android-устройств дополнительно настраивается приоритет (high для мгновенной доставки), channel_id для категоризации уведомлений в системном трее и click_action для обработки нажатия. Для iOS-устройств настраиваются параметры APNs: звук, бейдж (счётчик на иконке приложения) и content-available флаг для фонового пробуждения. Бэкенд формирует payload с учётом платформы получателя, определяя её по информации о зарегистрированном устройстве.

### 6.3 Схема интеграции

1. Приложение регистрирует FCM-токен устройства.
2. Токен отправляется на бэкенд и сохраняется в профиле абонента (в BSS).
3. При наступлении события (платёж, смена тарифа) бэкенд формирует push-сообщение.
4. Бэкенд отправляет запрос к FCM API с целевым токеном.
5. FCM доставляет уведомление на устройство.
6. Приложение обрабатывает уведомление и отображает его пользователю.

Жизненный цикл push-уведомлений начинается с регистрации устройства. При первом запуске приложения Firebase Messaging плагин автоматически получает уникальный FCM-токен от серверов Google, который идентифицирует конкретное устройство. Приложение отправляет этот токен на бэкенд через endpoint регистрации устройства, сопроводив его информацией о платформе (iOS/Android) и версией приложения. Бэкенд сохраняет привязку user_id → fcm_token → platform в своей базе данных.

При наступлении бизнес-события (успешный платёж, изменение баланса, ответ поддержки) бэкенд определяет целевых получателей, проверяет их настройки подписки на уведомления и формирует payload. Запрос к FCM API отправляется асинхронно через очередь сообщений (Redis), что обеспечивает высокую производительность и отказоустойчивость. При массовых рассылках используется multicast-режим, позволяющий отправить одно сообщение нескольким токенам за один запрос.

На стороне приложения Firebase Messaging плагин получает push-уведомление и обрабатывает его по-разному в зависимости от состояния приложения. В фоновом состоянии уведомление отображается в системном трее автоматически. В активном состоянии (foreground) плагин передаёт данные в обработчик приложения, который отображает кастомное уведомление или обновляет UI. При нажатии на уведомление приложение извлекает данные payload и выполняет навигацию на соответствующий экран через GoRouter.

При выходе пользователя из аккаунта приложение вызывает endpoint отвязки устройства, и бэкенд удаляет привязку FCM-токена от профиля абонента. При повторной авторизации процедура регистрации повторяется, что гарантирует актуальность привязок и предотвращает отправку уведомлений неавторизованным пользователям.

## 7. Сетевой слой приложения

### 7.1 API Client

Единый ApiClient на базе Dio обеспечивает: baseURL (production/emulator), interceptor для JWT Bearer токена, перехват ошибок и маппинг на доменные исключения, таймауты, логирование запросов (только в debug).

ApiClient является фундаментальным компонентом сетевого слоя приложения, обеспечивающим единообразную обработку всех HTTP-запросов к бэкенду. Он построен на базе библиотеки Dio, которая предоставляет мощные возможности для работы с HTTP: интерцепторы, трансформеры запросов и ответов, автоматический парсинг JSON, управление таймаутами и обработку ошибок.

Базовый URL ApiClient конфигурируется в зависимости от сборки (flavor): debug-сборка указывает на локальный эмулятор или staging-сервер, release-сборка — на production-сервер. Переключение осуществляется через переменные окружения или конфигурационные файлы, что исключает возможность случайного обращения к тестовому серверу из продуктивной сборки.

JWT Bearer interceptor автоматически извлекает токен из flutter_secure_storage и добавляет его в заголовок Authorization каждого запроса. При получении ответа 401 (Unauthorized) interceptor проверяет, не истёк ли токен, и если это так — инициирует процесс повторной авторизации. Если повторная авторизация невозможна, interceptor очищает хранилище и перенаправляет пользователя на экран входа.

Error interceptor перехватывает исключения Dio и маппит их на доменные исключения (NetworkException, AuthException, ServerException, PaymentException), которые обрабатываются на уровне Presentation. Каждое доменное исключение содержит человекочитаемое сообщение, код ошибки и опционально исходное исключение для отладки. Логирование запросов и ответов выполняется только в debug-режиме через специализированный логгер, который выводит информацию о методе, URL, заголовках, теле запроса и ответа, времени выполнения.

### 7.2 Remote Data Sources

- **UserRemoteSource**: авторизация, профиль.
- **BalanceRemoteSource**: счета, балансы.
- **ServiceRemoteSource**: услуги, тарифы.
- **TransactionRemoteSource**: история операций.
- **NewsRemoteSource**: новости/уведомления.
- **SupportRemoteSource**: обращения в поддержку.
- **PaymentRemoteSource** (НОВЫЙ): все операции с платежами (РСБ + СБП).
- **SmsRemoteSource** (НОВЫЙ): отправка и статус SMS.

Каждый Remote Data Source является узкоспециализированным классом, инкапсулирующим логику взаимодействия с определённой группой эндпоинтов бэкенда. UserRemoteSource отвечает за авторизацию (отправка PIN и пароля, получение JWT-токена, выход из системы) и получение профиля абонента. BalanceRemoteSource управляет запросами информации о лицевых счетах, балансах и ссылках на оплату.

ServiceRemoteSource обеспечивает работу с услугами абонента: получение списка активных услуг, доступных тарифных планов, дополнительных услуг, выполнение операций смены тарифа, подключения и отключения услуг. TransactionRemoteSource отвечает за запрос истории транзакций с фильтрацией по датам и пагинацией. NewsRemoteSource загружает новости и информационные уведомления от оператора. SupportRemoteSource отправляет обращения в техническую поддержку.

PaymentRemoteSource является новым компонентом, объединяющим все операции с платежами через оба платёжных провайдера. Он инкапсулирует запросы на создание платежа (карта или СБП), получение статуса, отмену и возврат. Для приложения нет разницы между РСБ и СБП — PaymentRemoteSource определяет провайдера по параметру payment_method и формирует соответствующий запрос к бэкенду. SmsRemoteSource отвечает за запросы на отправку SMS (в основном для OTP) и проверку статуса доставки.

### 7.3 Repository pattern

Каждый RemoteSource инкапсулирован в Repository (например, PaymentRepository), который: комбинирует данные из нескольких источников (BSS + РСБ + СБП), кеширует результаты, трансформирует DTO в доменные модели, обрабатывает ошибки.

Repository pattern завершает архитектурную цепочку от сетевого слоя к бизнес-логике. Каждый Repository реализует интерфейс, определённый в Domain слое, и предоставляет use cases удобный API для получения доменных моделей без знания о деталях реализации. Например, PaymentRepository может объединять данные из BalanceRemoteSource (для получения текущего баланса), PaymentRemoteSource (для создания платежа) и TransactionRemoteSource (для обновления истории), предоставляя use case единый метод processPayment(amount, method).

Кеширование на уровне Repository реализуется с использованием локального хранилища (Hive или Drift). Данные, которые редко изменяются (список тарифов, пакеты услуг), кешируются на длительный срок с инвалидацией по времени или по явному запросу. Данные, которые могут изменяться в любой момент (баланс, транзакции), кешируются на короткий срок или обновляются при каждом запросе (cache-aside стратегия).

Трансформация DTO в доменные модели выполняется внутри Repository с помощью методов-расширений или отдельных mapper-классов. Это гарантирует, что Presentation слой работает исключительно с чистыми доменными объектами, не содержащими технических деталей сериализации. Обработка ошибок на уровне Repository преобразует исключения сетевого слоя в доменные исключения с контекстом операции, что позволяет Presentation слою корректно отображать ошибки пользователю.

## 8. Схема данных и потоки

### 8.1 Поток оплаты картой (sequence)

App → Backend (GET /v1/.../pay-link?payment_method=card) → Backend → РСБ (POST MerchantHandler, command=v) → РСБ → transaction_id → Backend → App (client_handler_url) → App → WebView (ClientHandler) → Клиент вводит карту → 3DS → РСБ → RETURN_URL → Backend → App (deep link) → App → Backend (POST /v1/payments/card/status) → Backend → РСБ (command=c) → Backend → App (результат).

Полный поток оплаты картой состоит из десяти шагов и включает два полных цикла обмена между приложением и бэкендом. Первый цикл (шаги 1-3) инициирует платёж: приложение запрашивает платёжную ссылку, бэкенд регистрирует транзакцию в РСБ и получает идентификатор. Второй цикл (шаги 4-5) передаёт ссылку приложению и открывает WebView. Третий этап (шаги 6-7) — взаимодействие клиента с платёжной страницей Банка. Четвёртый цикл (шаги 8-10) завершает операцию: бэкенд получает redirect, опрашивает статус у РСБ и возвращает результат.

Критически важным моментом является обработка прерываний: если клиент закрывает WebView или теряет соединение на этапе ввода карты, транзакция остаётся в статусе CREATED/AUTHENTICATED и требует обработки. Бэкенд реализует механизм автоматического опроса зависших транзакций с интервалом 5 минут и таймаутом 10 минут, после чего транзакция помечается как expired. Это предотвращает accumulation неоплаченных транзакций в системе.

### 8.2 Поток оплаты СБП (sequence)

App → Backend (GET /v1/.../pay-link?payment_method=sbp) → Backend → СБП (POST /api/v1/create) → СБП → qrcode_link, order_id → Backend → App → App отображает QR → Клиент сканирует → Банк → СБП → Callback (POST /v1/payments/sbp/callback) → Backend обновляет статус → App может опросить статус.

Поток оплаты через СБП отличается от карточного отсутствием этапа ввода реквизитов на платёжной странице. После создания платежа (шаги 1-4) приложение отображает QR-код, и инициатива переходит к клиенту, который сканирует QR банковским приложением (шаг 5). Последующий процесс проходит вне нашего приложения: банк клиента обрабатывает перевод и отправляет confirmation в СБП, которая уведомляет наш бэкенд через callback (шаг 7).

Двухканальная модель обновления статуса (callback + polling) обеспечивает надёжность: callback обеспечивает мгновенное обновление при нормальном сценарии, а polling — обновление при сбоях в доставке callback. Приложение начинает polling сразу после отображения QR-кода с интервалом 3 секунды. При получении push-уведомления (инициированного callback) приложение немедленно запрашивает финальный статус и прекращает polling.

### 8.3 Поток SMS (sequence)

Backend определяет необходимость → Backend → Devino (POST /v2/Send/SMS) → Devino → SMS на телефон → Devino → Callback / Backend опрос (GET /v2/MessageState/{id}).

Поток отправки SMS полностью инициируется и управляется бэкендом. Приложение лишь косвенно запускает его через бизнес-операции (запрос OTP, создание тикета поддержки). Бэкенд формирует текст сообщения из шаблона, подставляя динамические параметры (код OTP, сумма, баланс), и отправляет запрос к Devino API.

Асинхронная обработка статуса доставки обеспечивается через callback от Devino или периодический опрос. При получении callback бэкенд обновляет статус в базе данных и, при необходимости, инициирует повторную отправку (например, если SMS не доставлено из-за временной недоступности номера). Мониторинг недоставленных сообщений позволяет оценить качество SMS-канала и вовремя выявить проблемы с доставкой.

## 9. Безопасность

Все внешние соединения защищены:

- РСБ — SSL/TLS 1.2+ с клиентским сертификатом (mTLS).
- СБП — HTTPS с аутентификацией по API-ключам.
- Devino — HTTPS с Basic Auth.
- FCM — HTTPS с OAuth 2.0 Service Account.
- BSS — HTTPS с JWT Bearer Token.

Хранилище: сертификаты и ключи — в secure vault / environment variables, JWT-токен пользователя — в flutter_secure_storage, FCM-токен устройства — на бэкенде в профиле абонента (BSS).

Безопасность архитектуры строится на многоуровневой модели защиты. На сетевом уровне все соединения между компонентами системы защищены протоколом TLS 1.2 и выше. Взаимодействие с платёжным шлюзом РСБ использует усиленную аутентификацию mTLS (mutual TLS), при которой обе стороны предоставляют SSL-сертификаты. Это исключает возможность перехвата или подмены данных в транзите и гарантирует, что только наш бэкенд может инициировать платежные операции.

Аутентификация с остальными сторонними сервисами также выполняется по защищённым каналам: СБП использует API-ключи, передаваемые в заголовках HTTPS-запросов, Devino — Basic Auth поверх HTTPS, FCM — OAuth 2.0 с JWT-токеном сервисного аккаунта, BSS — JWT Bearer Token. Каждый внешний сервис имеет собственный механизм аутентификации, и бэкенд хранит все учётные данные в secure vault или переменных окружения, недоступных для мобильного приложения.

На уровне мобильного приложения JWT-токен пользователя хранится в flutter_secure_storage — зашифрованном хранилище, использующем Keychain (iOS) и EncryptedSharedPreferences (Android). Это предотвращает извлечение токена даже при физическом доступе к устройстве. WebView для платёжной страницы РСБ сконфигурирован с валидацией URL (допускаются только домены rsb.ru) и отключённой возможностью навигации на произвольные сайты.

Валидация входящих webhook/callback от платёжных сервисов выполняется по нескольким критериям: проверка IP-адреса источника (для РСБ — по предоставленному Банком списку), проверка HMAC-подписи (для СБП — по ключу от Сбербанка). Это исключает возможность подмены callback от злоумышленника. Все секретные ключи, сертификаты и пароли хранятся в secure vault с ротацией по расписанию и аудитом доступа.

## 10. CI/CD и окружения

GitHub Actions workflow: lint → test → build (APK/IPA).

Переменные окружения (secrets):

- RSB_MERCHANT_URL
- RSB_CLIENT_URL
- RSB_SSL_CERT_PATH
- RSB_SSL_KEY_PATH
- SBP_API_URL
- SBP_API_KEY
- DEVINO_LOGIN
- DEVINO_PASSWORD
- FCM_SERVICE_ACCOUNT_JSON
- BSS_BASE_URL
- JWT_SECRET

Окружения: development (test URLs РСБ: testsecurepay2.rsb.ru), staging, production (production URLs РСБ: 3dsecurepay.rsb.ru).

Процесс непрерывной интеграции и доставки (CI/CD) реализован на базе GitHub Actions и обеспечивает автоматическое выполнение трёх этапов при каждом push в репозиторий. Этап lint запускает статический анализ кода (dart analyze, flutter lint) для выявления потенциальных ошибок и несоответствий стилю кодирования. Этап test выполняет юнит-тесты и виджет-тесты с генерацией отчёта о покрытии кода. Этап build собирает артефакты: APK для Android и IPA для iOS.

Секреты CI/CD хранятся в GitHub Secrets и инжектируются в workflow в виде переменных окружения. Это гарантирует, что учётные данные сторонних сервисов не попадают в исходный код и не доступны в репозитории. Каждая переменная окружения имеет чёткое назначение: RSB_MERCHANT_URL и RSB_CLIENT_URL определяют URL-адреса платёжного шлюза, RSB_SSL_CERT_PATH и RSB_SSL_KEY_PATH — пути к SSL-сертификатам для mTLS, SBP_API_URL и SBP_API_KEY — параметры подключения к СБП, DEVINO_LOGIN и DEVINO_PASSWORD — учётные данные SMS-шлюза, FCM_SERVICE_ACCOUNT_JSON — credentials для Firebase, BSS_BASE_URL — адрес биллинговой системы, JWT_SECRET — секрет для подписи JWT-токенов.

Три окружения (development, staging, production) обеспечивают последовательный путь от разработки до продакшена. Development-окружение использует тестовые URL платёжного шлюза РСБ (testsecurepay2.rsb.ru:9443) и тестовые данные, что позволяет безопасно тестировать полный цикл платежей. Staging-окружение зеркально повторяет production-конфигурацию, но работает с тестовыми данными и ограниченным набором пользователей для приёмочного тестирования. Production-окружение использует боевые URL (3dsecurepay.rsb.ru) и реальные данные с полным набором мер безопасности.
